# 策划日报 · Game Design Daily

面向游戏策划的中英文游戏日报，包含游戏动态与策划精选；Steam 市场和 AI 快讯与精选各有独立页面。

## 内容与版面

- 站点导航统一为“日报 / Steam 市场 / 小游戏榜 / AI / 信息来源”。日报中的游戏日报、策划精选属于“本期目录”，点击后跳到同一页对应栏目。
- **今日游戏日报**：近 72 小时尚未报道的游戏、新版本、产品观察、开发与行业动态，最多 16 条。日期缺失、未来日期不进入日报。
- **策划精选**：最多 3 篇机制、战斗、系统、关卡、玩家体验与开发复盘。允许较早文章，保留原始日期；深读需要实际取得正文。
- **AI 独立页面**：`ai.html` 展示最多 8 条短快讯和 2 篇精选，不受游戏条数限制。快讯采用 1–2 句概述，精选需实际取得正文；缺少合适内容时留空。AI 正式刊期单独保存在 `archive/ai/YYYY-MM-DD.html`，已有归档不覆盖。
- 中文摘要与英文原标题并列，保留来源、发布日期、类型、原文入口。日报直接展示本期全部内容。
- 选源并不等于证明每篇文章优质；先按来源、类型与时间筛选，再依据正文判断相关性和信息量。
- 同一事件的中英文报道尝试合并。语义去重失败时降级为 URL/同语言标题去重，并在运行日志记录限制。

## Steam 市场观察

市场统一为全局观察，包含动作游戏在内的各玩法方向；小体量独立游戏另设“小游戏榜”。日报首页通过导航进入市场页，市场摘要集中放在市场页开头。

- `market.html`：全局跨类型样本，包含动作。开头展示市场摘要，再展示近期升温、当前热门、新作观察和可展开的玩法分类；封面直达 Steam。标签可以重叠，不相加为市场份额。
- `market-action.html`：仅兼容旧链接，自动跳转到全局市场；不再作为独立栏目采集或展示。
- **发现范围**：全局样本来自全球热销前 100、最近发行前 100（无评论数门槛）和热门游玩前 50。以实时来源返回为准，排除 DLC、Demo、软件、未发售及资料不明项目。来源分别保存发现数、纳入数、时间与失败状态。不是 Steam 全库普查。
- **稳定样本**：初始最多 250 款，之后每天最多新增 8 款，持续保留至少 90 天，总上限 1000。保留低关注新作，已纳入作品不会因为跌出榜单而立即消失。
- **当前热门**：优先按已验证的全球热销榜入榜作品数排序，同数比较最高榜位。榜单按收入且包含 DLC、内购，但不公开金额；无法取得有效榜单时明确降级到样本在线合计。
- **近期升温**：1/7/30 天对比两个等长完整日窗口，每天至少两次有效采样且跨度六小时。同一批作品配对比较；至少 3 款、覆盖分类 60%，同时检查增长幅度、上涨数量、最大作品贡献与去除后的变化。低基数、单款带动、缺失不生成整体升温结论。窗口不足时显示待积累。
- **新作观察**：近 90 天作品，按发售年龄分组，卡片最近发售优先。已确认是抢先体验转正式版但首次发售日期不明的作品，排除新作分组、保留其他观察。累计评价是全部语言、全部购买渠道的过滤离题统计，不等于首 7/30 天表现。未生成销量、成功率、竞争饱和度或 ROI 结论。
- **工具状态**：VGI / Gamalytic 的销量和收入估算尚未接入；SteamPeek 仅保留手动研究入口，不能声称已经自动收集。
- **更新**：沿用北京时间每天四次市场采样，以及 08:30 日报时更新。全局发现与评价每日刷新，商店资料默认缓存七天；每次运行采集在线。GitHub Actions 排队可能延迟。
- **失败处理**：来源与字段独立标记旧值，失败不新增历史、不补零。全局采集默认预算八分钟，未完成项目标为延后采集并保留旧记录，下次优先采集较久未尝试的作品。1/7/30 天都使用北京时间，完整 30 天前后比较需要至少 60 个覆盖日。
- **保存**：全局在 `data/global_market.json`、`data/global_market_history.json`。原有 42 款跟踪样本的 `data/market.json`、`data/market_history.json` 保留为历史资料，不再用于日常采集或页面渲染。已归档日报不回填未来市场数据。

只更新市场，不调用模型、不更改日报文章、RSS 和记忆：

```sh
python src/global_market.py
python src/market_render.py
```

`market_render.py` 生成全局市场页与旧动作页的跳转页。来源和详细采样口径可在市场页底部展开；数据未接入和历史不足会明确显示。

## 小体量独立游戏观察

“小游戏榜”下分成四个独立页面，各自保留搜索、玩法筛选和清晰的数据口径：

| 页面 | 内容与时间口径 |
| --- | --- |
| `indie.html`：新上架（尚未发售） | 监测中首次发现的未发售游戏。近 1 / 7 / 30 天按本站 `first_seen` 筛选，它是本监测首次发现时间，不能当作 Steam 实际上架日期；入口排序变化也可能带来新发现。首次建立观察池的作品单列为基线，不计入新增。 |
| `indie-releases.html`：最近已发售 | 按已确认的首次可玩发售日期筛选近 1 / 7 / 30 天；包含抢先体验首次发售。已知从抢先体验转正式版、但首次日期尚未核实的作品不纳入新发售榜，避免把老游戏误报为新作。 |
| `indie-ratings.html`：好评率 | 原有最多 60 款已发售候选样本，按过去 1 / 7 / 30 天的好评数 / 评价数排序；至少 20 条期间评价才参与排名。评价窗口是采集时点向前 24 / 168 / 720 小时，以评论创建时间查询，所有语言与购买渠道、过滤离题活动。 |
| `indie-online.html`：当前在线 | 同一批最多 60 款已发售候选，按采样时同时在线人数排序；这是当前快照，不是近几天独立玩家数，也不是下载量。 |

小游戏没有 Steam 官方统一定义。好评率与在线榜沿用独立游戏热销、最近发行各前 100 条入口中的最多 60 款样本；最近发售页另从独立游戏最近发行入口分页发现，最多 1,000 条，确认列表日期已越过 30 天时提前结束。已发售候选以紧凑玩法标签和美国区原价不超过 25 美元或免费筛选，排除 DLC、软件、Demo 与未发售作品。

未发售页另查未发售入口前 300 条，价格未公布的作品允许纳入。发现采集预算为三分钟，未完成或失败会显示覆盖限制。这些都是有范围限制的研究候选池，不能据此证明开发团队人数、制作预算或囊括所有小游戏。

Steam 公开畅销榜按收入排序，具体销量和下载次数没有公开接口，因此不生成这些数字或将评论、在线人数换算成销量。仅在已采集的候选样本内比较。缺失不是零，旧值保留原时间并退出当前排名；未发售作品不进入好评率和在线榜。

`data/indie_market.json` 保存已发售候选的评价与在线数据；`data/indie_discovery.json` 保存新发现与最近发售数据。两者完整成功结果均缓存 23 小时、约每日采集一次，失败结果可在下一轮重试。发现数据持续保留监测基线和已见作品的首次发现记录，不能在例行更新时清空重建；作品暂时离开入口后再次出现，不重新计作新增，仍在 30 天内的旧发售样本继续保留。

现有日报与市场工作流按“榜单采集 → 发现监测 → 四页渲染”的顺序运行，并提交两个数据文件及四个页面。页面保留各自数据的实际采集时间，全程不调用模型。独立刷新：

```sh
python src/indie_market.py
python src/indie_discovery.py
python src/indie_render.py
```

`indie_render.py` 一次生成四页，完整试刊构建也包含这四页及相互导航。市场更新不改日报文章、RSS 和记忆，不重写历史日报归档。

## 正式版与本地预览

正式刊期保存在 data/digest.json，生成 docs/index.html、docs/feed.xml 与按日归档。首期使用已经人工查阅和审核的内容；后续刊期由每日管线生成。是否已上线以 GitHub Actions 的部署结果和线上页面为准。

data/preview_digest.json 保留审核时的试刊样本，与正式成稿、发布记忆和历史归档分开。预览页面显示“试刊”。

无模型密钥也可生成这份预览：

    python src/build_preview.py docs/preview-site
    python -m http.server 8765 --bind 127.0.0.1 --directory docs/preview-site

打开 http://127.0.0.1:8765/，即可查看完整试刊、来源目录和试刊 RSS。这个构建只使用已审核的试刊内容，不需要模型密钥，也不改正式刊期或发布记忆。

只更新仓库里的单页预览时：

    python src/render.py data/preview_digest.json docs/preview.html
    python src/feed.py data/preview_digest.json docs/preview-feed.xml

试刊不会写入正式按日归档或发布记忆。

## 来源

主要入口包括 GameRes、机核、触乐、indienova、Game Developer、GamesIndustry、80.lv、Dan Felder、Unreal Engine 与 Unity。
AI 来源包括官方博客与实践型作者，候选保留 30 天以供精选筛选，快讯仍限定近期 72 小时。源配置详见 src/config.py。

多平台来源单独登记，采集上限为每源通常20条、合并后最多1200条；游戏日报最多16条、精选3篇，AI 页面最多8条快讯、2篇精选。目录：

- data/public_sources.json：10款不同类型游戏的 Steam 官方公告、Factorio Friday Facts、Riot 开发文章、itch.io 项目日志。
- data/creator_sources.json：YouTube 创作者、中文作者网站、腾讯游戏学堂官网及手动公众号线索。
- data/community_sources.json：当前为空。Reddit、Discord 已退出采集流程；B站的两个受限来源也已移除。
- docs/sources.html：来源目录、本轮采集数量、空窗、访问失败、待授权和手动收录状态。空窗不等于连接失败；登记也不等于已经采到内容。

来源页将正常读取（含窗口内无新内容）、部分读取、访问受限、读取异常、待接入和手动入口分别统计。部分文章详情失败、视频仅回退到频道页标题时标记“部分读取”；失败或尚未接入的来源不显示成“已读取 0 条”。Steam 公告等低频来源保留原时间窗口，报告会注明排除原因与本轮最新原文日期。网站 / RSS 请求对超时与部分 5xx 最多重试一次。Steam 公告与市场 API 共用线程独立的连接池，API 并发最多 2 路，明确的 TLS 提前断开也最多重试一次；保留环境代理和证书校验，权限限制、限流及证书错误不重试。

只检查来源、刷新来源页而不重新生成日报，可运行 `python src/fetch_sources.py` 和 `python src/source_directory.py`；候选、健康报告随检查更新，已发布文章不改变。来源页的检查时间独立于市场快照时间。

Steam 单期至多4条，同一来源通常至多3条；热度不作为可信度。扩充候选不扩大日报版面。来源配额不会强迫填满栏目。

视频标题/简介保留为待看线索，无字幕时不生成视频分析；缺日期不冒充今天。社区完整的公开文章或自述还需通过正文相关性检查；提问、只有外链、上下文不全的聊天保留在 ranked.json 的 review_queue，不进入成稿。跨语言去重以120条一批执行，跨批次仍可能有同事件重报，URL/完全相同标题会先全局去重。

**已退出的来源**：Reddit、Discord 与 B站不再列为当前来源，也不会在定时任务中采集。对应解析器保留但未启用；工作流不再读取社区访问凭据。移除来源后，旧报告也不会把入口重新带回来源页。

**知乎相关内容**：目前没有直接自动采集知乎。已接入知乎作者叶梓涛的公开个人网站「落日间」，来源页提供经作者主页核验的知乎个人页链接。网站中的无准确日期长文作为经典阅读候选，不冒充当日新闻。

**手动补充线索**：复制 data/source_inbox.example.json 为 data/source_inbox.json（已忽略提交），填写公开链接对象列表，可含url、title、source、source_id、platform、published、lang。文件仅收集线索，标题或日期不会被当作已核验正文；review_queue中再核验。私密消息不要放进公共来源列表。

RSS 和公开文章列表分开处理；不会猜测不存在的 feed。设计源可使用 30 天窗口，新闻默认 72 小时。
data/reading_library.json 保存从收藏与研究中挑选的常青备选：GDKeys、Game Design Skills、The Level Design Book 等。
经典文章只有在近期精选不足、取得正文且未近期报道时才可能入选。演讲如果只有简介、没有字幕，不能冒充完整精读。

## 管线

    python -m venv .venv
    pip install -r requirements.txt

设置 DEEPSEEK_API_KEY 后依次运行：

    python src/fetch_sources.py
    python src/cluster.py
    python src/rank.py
    python src/readfull.py
    python src/summarize.py
    python src/render.py
    python src/ai_render.py
    python src/source_directory.py data/source_report.json docs/sources.html
    python src/feed.py
    python src/commit_memory.py

模型用于跨语言去重、标题翻译、摘要与正文相关性检查。排序和栏目配额由代码控制。
没有密钥时，可以显式运行 summarize.py --offline 验证管线；只保留来源摘要，不生成翻译/深读，不写正式发布记忆。

## GitHub Pages 发布

现有地址保持不变：[策划日报](https://vizroi.github.io/daily-ai-digest/)。工作流有以下入口：

- **推送到 main**：运行测试，然后直接上传并部署仓库中的 docs。首次推送不会重新抓取或调用模型，因此保留已审核的首期内容。
- **每日定时或手动 daily**：只在 main 运行抓取、筛选、摘要、市场采集、渲染、RSS 和记忆更新，提交生成结果后，直接上传并部署同一份 docs。每日计划为北京时间 08:30；GitHub 排队可能导致延迟。
- **市场定时或手动 market**：采集全局市场和独立游戏候选，保存市场历史及发现监测记录，更新市场观察页和小游戏的四个页面；不改日报首页、RSS、发布记忆或历史刊期。
- **手动 publish**：发布仓库已生成的 docs，不重新采集。手动运行请选 main，并按用途选择 mode。
- **手动 sources**：在 GitHub Actions 环境单独检查来源并发布来源页，只提交来源报告、健康记录和 sources.html；不调用模型或重做日报。可用于区分本地网络故障与线上采集问题。

各入口共用同一并发组，避免同时发布。写入任务从最新 main 检出，推送前 rebase；冲突会阻止发布，不强制覆盖。生成任务取得 contents:write；独立部署任务只取得 pages:write 和 id-token:write。工作流直接部署 Pages 产物，不依赖机器人提交再次触发构建。

仓库需要启用 GitHub Pages。建议在 Settings → Pages → Build and deployment 中将 Source 设为 GitHub Actions；若保留分支发布，来源分支必须为 main，目录为 /docs，且 github-pages 环境规则允许 main 部署。详情见 [GitHub 官方部署说明](https://github.com/actions/deploy-pages#security-considerations)。生成日报摘要需在仓库 Actions Secrets 配置 DEEPSEEK_API_KEY；单独检查来源无需模型密钥。

工作流文件通过本地检查不代表部署已经完成。发布后应查看 Actions 的 deploy 结果，再核对线上首页、来源目录和 RSS；新内容管线也需要一次实际运行验证。

## 证据边界

- 原始发布日期和 updated 分开；抓取时间不是发布日期。
- RSS 摘要、RSS 内容字段、网页正文分别保存，不按摘要长度冒充全文。
- 取得正文失败的近期精选退回日报简述；旧文不会被补成当天新闻。
- 只依据实际材料归纳。作者观点与编辑阅读角度明确区分；缺失事实不补写。
- 转载数量不自动证明独立验证；页面不展示伪精确的质量分数。
- 30 天发布记忆记录事件 key 与原文链接；同一天重跑不重复计数。
- 没有合适内容就展示真实空状态，不用热门仓库、泛 AI 论文或求助帖填满版面。
